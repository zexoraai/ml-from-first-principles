Tier E — mechanisms Tier R — trained model checking parity…

Decoder-only GPT, with a working KV cache

A byte-level BPE tokenizer trained from scratch, pre-norm transformer blocks, GPT-2's scaled residual initialisation, tied embeddings, an incremental KV cache, and the three sampling controls people conflate — temperature, top-k and nucleus. All of it runs in your browser, streaming, at a measured tokens-per-second you can watch.

Attention is reused from Project 1, not rewritten: GPT's causal self-attention is exactly the original Transformer's decoder self-attention, so a second copy could only drift.

The research question

What does it take to make an autoregressive language model that is genuinely usable interactively — not just trainable?

Project 1 established that attention works. This project is about the gap between “the maths is right” and “a person can type into it and get an answer before they lose interest.” Three things close that gap, and each one is a component here rather than a note:

  • A tokenizer that cannot fail. Byte-level BPE has no unknown token, so no input can break it — which removes an entire class of production bug.
  • A KV cache. Without it this model needs about 2.7 seconds per token in a browser. With it, about 15 milliseconds. That is not an optimisation; it is the difference between having a demo and not.
  • Sampling controls that do what they say. Temperature, top-k and top-p act on the distribution in three different ways, and the interface shows all three acting.
What is and is not claimed

Mechanisms are tier E, verified against oracles and invariants. The trained model is tier R: a small GPT trained to convergence on a ~1.1 MB corpus. No GPT-2 benchmark result is reproduced or claimed. The ~124M-parameter configuration exists in the code as GPTConfig.gpt2_small() for cost estimation only, and was not trained — see Environment & method.

How your prompt is tokenised

The tokenizer is byte-level BPE trained from scratch on this corpus — not tiktoken, not GPT-2's released vocabulary. Ids are ours and interchange with nothing. Because it starts from the 256 byte values, every possible string is representable and there is no unknown token: try pasting emoji or Japanese and watch it fragment into bytes rather than fail.

Where the newest token looked

These pictures are not explanations

An attention row is a faithful record of one weighted average, in one head, at one layer, for one input. It does not show that the information was used: the head's output passes through WO, which can project it somewhere the rest of the network ignores, and the residual stream carries information around it. Establishing use needs intervention — ablate the head and measure the logit change, or patch its activations from a different input — not inspection. None of the numbers in Results depend on reading these.

Does the browser agree with PyTorch?

Sampling is stochastic and JavaScript's PRNG cannot reproduce torch.multinomial, so sampled text is deliberately not compared — that test would be either meaningless or rigged. Everything deterministic is compared: raw logits, the argmax, and a full greedy continuation, which compounds any drift over many steps and is exactly where a cache or position bug would surface.

The same check runs headless via scripts/verify_js_parity.mjs, so the badge is not self-reported by the code under test.

Architecture, and every place it differs from Project 1

GPT-2 is not the 2017 Transformer with the encoder deleted. Six things differ, each is a deliberate choice by the GPT authors, and each is implemented here rather than glossed over.

The KV cache, with the arithmetic

Keys and values for positions already generated never change — they depend only on their own position's input. Recomputing them each step is pure waste, and at this model size the waste dominates everything else.

Multiply-accumulates per newly generated token, 6 layers, d_model 192, context 192. Analytic counts, matching GPT.estimate_flops_per_token.
PathMACs per token Est. browser time
Re-encode the whole context~550 M~2.7 s

What the cache does not save: the query projection, the output projection and the MLP still run for the new position, and attention still reads every cached key. It removes redundant recomputation, not the inherent linear-in-context cost of attending.

Why this is safe to ship

A cache is only sound if it changes nothing. tests/test_p2_cache.py requires cached and uncached generation to produce token-identical output across four sampling configurations, and separately requires that feeding a sequence one token at a time equals one masked pass over the whole thing.

The bug it exists to catch: using positions 0…n-1 for the new tokens instead of n_past…n_past+n-1. Every generated token then gets position embedding 0, output stays fluent for a few tokens and then degenerates — a failure that looks like a bad model rather than a bad cache. A dedicated test pins it.

The tokenizer, trained from scratch

Byte-level BPE, following Sennrich et al. (arXiv:1508.07909) for the algorithm and GPT-2 for the byte-level variant. Start from the 256 byte values, then repeatedly merge the most frequent adjacent pair. The merge list is ordered, and that order is the model: encoding replays merges by rank, and applying them in any other order produces different tokens for the same string, silently invalidating every checkpoint.

  • No unknown token, ever. Every byte sequence is representable, so the tokenizer cannot fail on an input.
  • Pre-tokenisation stops merges crossing boundaries. Without it BPE cheerfully learns a single token for ".\nThe", spending vocabulary on formatting artefacts. A leading space stays attached to its word, which is how the model learns word boundaries without a separate marker.
  • Trained on the training split only. Fitting the merge list on the whole corpus would let held-out text be represented more efficiently than genuinely unseen text — a small leak, free to avoid.
  • vocab_size is a target, not a guarantee. A corpus can run out of pairs worth merging. The model's embedding table is sized from the tokenizer's real vocab, because a caller that assumed otherwise would allocate rows that can never be indexed.

Temperature, top-k and top-p are three different things

These get conflated constantly. Precisely:

p ∝ exp(z / T)
temperature

Rescales the logits. T→0 approaches argmax; T=1 is the model unmodified; T>1 flattens. It changes how sharply the model's ranking is followed and never reorders it — pinned by a test. It also never removes a token.

keep the k highest, renormalise
top-k

Truncates. Removes the long tail entirely, which is what prevents the rare-but-catastrophic token. Fixed width regardless of how confident the model is.

smallest set with Σp ≥ p
top-p / nucleus

Adaptive. One or two tokens when the model is confident, many when it is not — usually what people actually wanted from top-k. Never empty: the token that crosses the threshold is kept.

Order of application is temperature → top-k → top-p, in both the Python and the JavaScript. Truncating first would let temperature reintroduce nothing, since the removed mass is already gone — so the order is load-bearing, not arbitrary.

A real bug this project had

Top-k was first implemented as masked_fill(logits < kth_value, -inf). That keeps every token tied at the threshold, so top_k=10 on a near-uniform distribution returned 50 candidates. It is not a corner case: a freshly initialised model is nearly uniform, so ties at the cut are the normal case early in training, and the bug silently disables top-k exactly when it matters most. Both implementations now select by index. Found by test_top_p_adapts_to_confidence_where_top_k_does_not.

Metric definitions, before any values

  • validation cross-entropy — mean loss per BPE token on held-out contiguous text, in nats, averaged over 200 random windows. Averaging matters: a single window is noisy enough that consecutive evaluations can differ more than a real improvement.
  • perplexity — exp(loss), per BPE token on our own 1024-token vocabulary trained on this corpus. It is not comparable to per-character or per-word perplexity, nor to any model with a different tokenizer. Quoting it against a published figure would be meaningless.
  • train − val gap — the overfitting indicator. On a 1.1 MB corpus with ~20 passes over it, some gap is expected and its size is the honest thing to report.

Limitations

  • The model is 2.9 M parameters trained on 1.1 MB. It learns Shakespeare's form — speaker labels, line breaks, cadence, plausible morphology — and it does not learn facts, reasoning, or long-range coherence. It is far below the scale at which those appear. Judge it on form and nothing else.
  • No GPT-2 result is reproduced. Not attempted. The 124 M configuration is in the code for cost estimation only.
  • Perplexity is tokenizer-specific and not comparable to published numbers.
  • 192-token context. Learned position embeddings cap it. Beyond that the model genuinely cannot represent older text; the interface rebuilds the cache and says so.
  • Single seed, no variance estimate.
  • Greedy/sampled decoding only — no beam search, which is the right choice for open-ended generation but is a stated absence.
  • The corpus is one author in one register. Prompt it with modern prose (there is a preset) and watch it pull everything back towards blank verse. That is the training distribution asserting itself, and it is the most honest thing on the page.
  • Timings are lower bounds — the training machine shares an unrelated 37-container stack (details).

Reproduce it

git clone https://github.com/zexoraai/ml-from-first-principles
cd ml-from-first-principles
docker build -t ml-labs:cpu .

# correctness suite: tokenizer, model, sampling, KV cache
.\run.cmd python -m pytest tests -q

# train (downloads TinyShakespeare once; ~2 h on 6 CPU threads)
.\run.cmd python scripts/train_p2.py --run-name p2-shake-3m --steps 1800 --warmup 150

# export for the browser, with a parity fixture
.\run.cmd python scripts/export_p2_web.py \
    --checkpoint runs/p2-shake-3m/checkpoint_best.pt \
    --result runs/p2-shake-3m/result.json

# verify the JS engine agrees with PyTorch, headless
node scripts/verify_js_parity.mjs

Data and licence

TinyShakespeare: Shakespeare's works are public domain; the compilation is distributed under the MIT licence of karpathy/char-rnn. Nothing is scraped. The split is a contiguous 90/10 cut by character position — not a shuffle, because neighbouring windows overlap almost entirely and shuffling them would put near-duplicates on both sides of the split.
