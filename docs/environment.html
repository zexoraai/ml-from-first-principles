Finding 1 — PyTorch could not load at all, and the obvious fix was the wrong one

pip install torch succeeded. import torch did not: 

OSError: [WinError 4551] An Application Control policy has blocked this file.
Error loading "...\.venv\Lib\site-packages\torch\lib\shm.dll"
or one of its dependencies.

Not a broken install. The host has Windows Smart App Control enabled and enforcing, confirmed in the registry (VerifiedAndReputablePolicyState = 1). Smart App Control refuses to load binaries it does not judge verified-and-reputable, and PyTorch's Windows wheels ship unsigned DLLs. numpy imported fine — its binaries are signed — which is what localised the cause to code signing rather than to the package.

The rejected fix

Every guide says to turn Smart App Control off. It would have worked. It was rejected on two grounds: it is a machine-wide security downgrade affecting every application on the machine, made to satisfy one dependency; and it is close to irreversible — historically, re-enabling required resetting or reinstalling Windows, and only recent Windows builds can re-enable it without a clean install. Trading that for a pip install is a bad trade.

What was done instead

Smart App Control governs Windows binaries, not Linux binaries running inside the WSL2 virtual machine — and Docker was already installed. All Python now runs in a pinned Linux container. PyTorch loads normally, and the host's security configuration was never touched. The constraint produced a better setup than the one originally planned: a Dockerfile plus a per-run dependency snapshot is a far stronger reproducibility record than “it worked on my laptop”.

Finding 2 — the first benchmark was wrong by 300×

Worth dwelling on, because the wrong numbers looked entirely plausible. Here is what the first benchmark reported, and what was actually true:

Same workloads, same machine. Only the timing harness changed.
Workload First harness Corrected Error
128² fp32 matmul31.68 ms0.104 ms305×
2048² fp32 matmul252.2 ms · 68 GFLOP/s95.8 ms · 179 GFLOP/s2.6×
0.53 M-param training step4,979.7 ms100.5 ms50×

The tell was not a suspicious absolute value — it was an internal contradiction. The same run reported a 27.29 M-parameter training step at 1,147 ms and a 0.53 M-parameter step at 4,980 ms. A model performing strictly more arithmetic cannot finish sooner. Something outside the computation was being measured.

The cause: each timing sample wrapped exactly one call. That pays a large fixed cost on entry to every timed region — consistent with PyTorch's intra-op thread pool parking between calls and being rewoken, which is expensive under a hypervisor. Warm-up and taking a median did not help, because every sample paid the cost. The fix is standard: choose the inner repeat count at runtime so each timed region lasts long enough that entry cost and clock granularity are negligible.

Why the bad run is still published

env-bench-01 remains in the evidence register, marked INVALID. Deleting it would erase the most transferable lesson here. And it mattered: reading “68 GFLOP/s, 5 seconds per step” as a property of the hardware would have baked a ~50× error into the compute estimate for all eight projects, and would have made several of them look infeasible when they are not.

Finding 3 — the machine is not a benchmark host

During measurement, 37 unrelated containers were running on this machine — OpenSearch, ClamAV, around ten Postgres instances, Redis, MinIO, MongoDB, Temporal, LiteLLM and several application services — all up for seven hours. They belong to other work and were left running.

Identical workloads, minutes apart, under different contention.
WorkloadQuieterContendedRatio
2048² matmul, 6 threads95.8 ms266.6 ms2.8×
256² matmul, 4 threads1.36 ms19.17 ms14×
0.53 M-param step, 2 threads100.5 ms278.9 ms2.8×

Consequently: every timing in this portfolio is a lower bound on the hardware's capability, every benchmark record carries a system-load snapshot so an outlier is annotated rather than mysterious, and extrapolated training durations are given as ranges spanning both regimes rather than as single numbers.

One conclusion survived every contention level and is therefore acted on: small models train fastest at 2 threads and are three to six times slower at 6, while large matmuls do scale to 6. Thread count is set per workload rather than once globally.

Method commitments

  • Benchmarks: warm-up before timing, adaptive inner repeats so each timed region lasts ~0.3 s, median of repeated blocks with min and max retained so throttling is visible rather than averaged away, thread count reported always.
  • Correctness before performance: every mechanism is checked against an independent oracle and a naive transcription of the paper's equation before any speed claim is made about it.
  • Masking is proved behaviourally, not by inspecting a weight matrix. Perturb a future token; require earlier outputs to be bit-identical. A transposed mask passes the weaker check and fails this one.
  • Evidence schema: run identifier, source commit, seeds, dataset version and split, dependency set, hardware, duration, metric definitions stated before metric values, checkpoint checksum, and a reproduction command. A number without a run identifier does not get published.
  • Repeats where cheap: runs under ten minutes get at least three seeds and report a range. Expensive runs are labelled single run, no variance estimate and no significance is claimed from them.
